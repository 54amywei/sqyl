# 看板 AI 协作交付流程

## 目标与角色
Codex 协助分析、计划、实现和初步检查；需求方确认业务目标与指标口径，开发负责人确认技术方案并审核代码，发布负责人管理环境和上线。

## 标准流程
1. **信息分级**：确认仓库可见范围；公开仓库只放已批准公开的内容。金融经营数据、客户信息及未脱敏截图不得进入公开仓库、公开预览或未经批准的 AI 对话。
2. **原型走查**：确认用户、决策场景、页面范围、导航和交互。逐项确认指标定义、公式、单位、期间、维度、数据源、更新频率及缺失/异常处理。
3. **Codex 只读分析**：先让 Codex 盘点页面、交互、未知项、风险和开发拆分，不修改文件。
4. **人确认规格与计划**：业务确认口径，开发确认架构、数据接口、权限和验收方法；未决事项标记负责人和状态。
5. **小步开发**：一个 GitHub Issue 对应一个可验收任务；从 main 建 feat/fix 分支，用 Codex 实现已批准范围。
6. **检查与预览**：开发者检查完整 diff 并运行项目现有验证；UI 改动提供与当前提交对应的预览。使用符合数据级别的受限环境。
7. **人工评审和业务验收**：处理阻断意见后，由开发人工审核；业务按指标基准和交互清单验收。AI review 不能替代人工批准。
8. **合并、发布、留痕**：PR 合并后按授权流程发布，记录版本、提交、环境、责任人、验收和回滚步骤。
9. **复盘复用**：记录返工原因、PR 周期、验收通过率和模板缺项，只把验证有效的约定更新回仓库。

## 最小 GitHub 设置建议
- 明确仓库可见范围和读写角色；main 通过 PR 合并。
- 建议要求至少一名人工审核并解决评审意见后合并；不要只依赖 AI review。
- Issue 与 PR 使用模板；每项工作关联 Issue。
- 原型批准标签（如 prototype-v1.0-approved）与生产版本（如 v1.0.0）分开。
- GitHub Pages 会公开发布静态资源；仅在内容获准公开时用于预览。页面里前端隐藏内容不构成访问控制。

## Codex 每次任务的用法
先只读盘点 → Codex 列问题与计划 → 人确认 → 小范围实现 → 检查 diff/验证 → PR 人审 → 业务验收。
